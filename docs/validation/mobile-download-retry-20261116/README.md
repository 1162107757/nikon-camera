用户提供“下载请求较多，请稍后再试”截图，并确认已经重试过几次。新版 Android/iOS 下载原来使用同一个 RPC，每一次签发下载跳转都按完整安装包大小预留流量，包括短时间内对相同文件的重试。229 APK 为 53,264,170 字节，十次这样的请求累计 532,641,700 字节，再请求即超过单个网络每小时 512 MiB 的上限。线上观察到这一大小的来源桶；截图本身没有请求标识，不能把该桶与用户请求作唯一关联。

## 修复与范围

- 新增 `024-mobile-download-retry.sql`：同一来源、同一 SHA-256、同一文件大小在固定十分钟窗口内，只预留一次文件流量；重试不延长窗口。缓存 304 不增加文件流量。
- 所有请求仍计次数。保留每 IP 每小时 20 次/512 MiB、全站每日 1000 次/5 GiB 上限，以及所有历史计数。统计的是签名下载授权的预留流量，不是 COS 实际传输字节。
- 新 RPC 与旧 RPC 使用相同的事务锁和已有计数键，允许滚动部署期间旧实例继续调用。原有 RPC 定义保持不变，新 RPC 只授予 `service_role` 执行权限。
- 下载接口区分当前网络与全站限流，返回对应错误及真实 `Retry-After`；浏览器显示范围和剩余等待时间，Android/API 继续得到 JSON。
- 不回退发布记录，不清空额度，不改变已发布 APK、强更策略或客户端版本。旧限额仍可能在本小时或本日内生效，新部署不会退还之前已预留的流量。
