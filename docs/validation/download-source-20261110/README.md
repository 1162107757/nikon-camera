# 官网下载限流来源修复

2026-11-10，工作目录 `D:/dev/ai-project/nikon-camera`。

## 问题与根因

用户从官网下载时出现“下载请求较多”。线上数据库的两个公开版本 RPC 已按 IP 隔离，没有全站共享额度；但官网比云网关直连多经过自有 Lighthouse 代理。固定的 4 跳配置在官网入口取到了代理地址 `118.24.164.117`，把不同官网用户合并到同一个 IP 桶。

使用服务端现有 HMAC 算法核对该代理地址，命中了已达 60 次的下载桶。修复前，同一客户端在直连和官网入口得到两个不同的来源标识；用户伪造 XFF 不改变这一结果。来源探测的公开记录只保留匿名编号，没有真实客户端 IP 或来源哈希。

## 修复

- 保留已验证的云网关 4 跳和直接连接代理白名单。
- 新增 `TRUSTED_FORWARDED_PROXY_ADDRESSES`，生产环境只配置自有代理的精确 IP `118.24.164.117`。
- 网关链之外，只跳过明确配置的可信代理，遇到第一个客户端 IP 即停止；不依据 Host、任意 XFF 长度或用户提供的首个地址决定来源。
- 官网与直连对同一个客户端使用相同额度，不同客户端独立；已有 IPv4 规范化、IPv6 `/64` 归组和非法来源拒绝逻辑保留。
- 真正命中 IP 限流时，网页显示“当前网络下载已达上限”和实际等待分钟数；Android／API 的 JSON 错误及 Retry-After 协议保留。

下载次数、流量上限、数据库函数和已有使用记录没有重置或放宽。没有发布新 App 版本，也没有改动 APK。

## 验证与部署

- 针对性测试 23/23 通过，包含代理问题重现、不同客户端隔离、直连一致性、伪造前缀／可信代理字面量、Host 伪造、非法配置、socket 信任边界、IPv4 映射、IPv6、完整 HTTP handler 和 IP 限流提示。
- 后端完整测试共 208 项：201 通过，0 失败，7 项因旧版 APK 固定测试文件未提供而跳过。另用现有 186 安装包执行真实 APK 容量测试，2/2 通过；79 个 JavaScript 模块语法／源码检查通过。
- 以线上现有代码包为基线，只覆盖 5 个后端模块，其余 45 个归档条目保留。源码基线与 Git 核对，部署后重新下载代码归档，全部 50 个条目逐字节核对一致。
- 线上配置只新增精确代理白名单，原有环境变量、角色和数据库限流函数核对保持不变。
- 官网／直连、正常／伪造 XFF 共 4 次线上来源检查均归于同一个真实客户端，且不再使用官网代理的身份。
