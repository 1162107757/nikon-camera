# 边拍边传调度优化

用户要求检查 Wi-Fi 下边拍边传速度。代码确认“同步 → 边拍边传”的成功路径存在两类无条件等待：预览保存后将同一张原图推迟 250 ms；每轮工作结束后，只要还有队列或元数据就等待 250 ms。连续照片会累计等待，即使相机与存储已经准备好。

97 在事务之间继续让出单线程相机执行器，但对已就绪的工作立即排队。预览成功后的原图 ready 归零；下一轮根据队列首项、元数据及新照片事件的真实就绪情况决定是否立即运行。无就绪工作时仍按原规则等待，忙碌／元数据退避截止时间、原图顺序、取消屏障、单一 PTP 会话、3 秒漏事件补偿与字节完整性校验保持。没有盲目加并发连接、修改 TCP 窗口或降低输出质量。

遥控拍摄页面的“拍后传入 App”使用 downloadPhoto，未经过上述两个固定等待。本轮不宣称该入口有同样收益；它的真实耗时需要结合相机原图大小和现有连接诊断中的 0x1009 操作用时测量。

## 比较方法和限制

运行 tests/run-album.ps1 的 LiveThroughputOnly 模式，生产 AlbumController 和 PtpIpClient 通过同一个合成内存 PTP 夹具，发现并接收 8 张各 1 MiB 的 JPEG；包括预览、原图接收、校验、私有保存及项目关联。相同测试源码分别编译优化前后生产源码，输出为 throughput-before.txt 和 throughput-after.txt：4346 ms → 420 ms。19 项完整性检查均通过，每张仅一次原图下载，预览先于原图，已有照片不重传，不写入相机。

该夹具不包含物理无线链路、相机写卡、手机存储性能、系统相册发布；结果只验证消除 App 固定等待，不能称为真实 Wi-Fi 吞吐、MB/s 或相机提速倍数。只各运行一次，无统计分布或实机外推。基准没有机器相关的硬性耗时断言。

完整 tests/run-album.ps1 回归通过：889 条生产控制器检查、33 条机型能力检查、22 条连接网关检查、356 条项目保存检查和 100 条目录关联检查；包括忙碌、漏事件、重复事件、变化描述符、不完整原图、取消、相册独立发布和重试场景。PTP 解帧实现没有改动，不重复运行已通过且输入未变的 96 全套协议测试。

优化前源码保留于 .tooling/remote-capture-97/AlbumController-before-performance.java；SHA 为 performance-source-before.sha256。最终源码 SHA、APK SHA 和本轮三项生产差异见 FINAL-IDENTITY.json。94–96 安装包保持原样。
