# 原图下载慢：2026-10-25 补充调查

用户明确：照片已出现，但原图下载很慢。97 去掉的是边拍边传的预览后／事务间排队等待，不能据此解释或宣称解决持续原图吞吐慢。

## 已完成的代码和 TCP 检查

原图通过一次 0x1009 GetObject 持续接收，接收块及写文件缓冲均为 256 KiB，未发现人为固定带宽上限或按块 sleep；进度通知最多每 200 ms 一次。原图流接收与预览使用不同的表示。相机 PTP 事务串行，真实相机发送和无线网络仍未测量。

新增可复用 tests/run-ptpip-throughput.ps1 和 PtpIpTcpThroughputBenchmark.java：真实本机 TCP 的两个连接完成 PTP 握手，32 MiB 合成原图字节以 1/16/64/256 KiB PTP 数据包接收，每种 3 次；验证完整字节数、CRC32、单调进度及下一次事务边界。不连接实体相机、不涉及 Wi-Fi、图像解码或手机磁盘，也不是原图的实际拍后可用延迟。

调查发现每次底层 read 都重复设置 SO_TIMEOUT。试改为同一原图事务中仅在超时值变化时调用。1 KiB 包的选项设置次数从约 102,000 次降至 1 次，但整体吞吐没有稳定提升。各组耗时中位数如下，单位毫秒：

| PTP 载荷 | 97 | 超时缓存试改 |
| --- | ---: | ---: |
| 1 KiB | 436.848 | 394.706 |
| 16 KiB | 368.879 | 388.430 |
| 64 KiB | 349.840 | 350.144 |
| 256 KiB | 332.599 | 377.210 |

数据不支持把该试改作为稳定提速发布；不能用桌面回环速度推断用户手机与相机链路。试改已撤回，全部 214 项生产输入和已交付 97 哈希完全一致，未生成或发布 98 安装包。保留真实 TCP 基准工具、原始 before/after 输出和试改证据，以便后续实机分析。
